# Device driver actions (firmware 0.3.6)

Wire-v1 profiles remain supported. Wire-v2 adds profile map key 14, an array of
`[action_id, first_sample_op, op_count]`. IDs are unique in 1–8. Slices are
contiguous, cover the existing shared sample-op pool (16 operations total), and
end with EMIT_RECORD. Init and safe-stop sequences remain shared by the device.
No additional static operation pool is allocated.

LOAD_ARGUMENT (opcode 26) uses the eight-word operation tuple:
`[26, dst, argument_id, required, width, little_endian, default_low, default_high]`.
Widths are 1–8 bytes; parameter IDs are 1–8. Required arguments, integer overflow,
byte lengths, duplicate and unused arguments are checked before any bus access.
Arguments support unsigned/signed integers, booleans and fixed-length bytes.
LOAD_ARGUMENT is allowed only in action sequences. Result fields must specify
their EMIT_FIELD byte width. Actions may emit a subset of the shared schema,
including no fields for a write-only action.

MODULE_COMMAND retains keys 0 (module key) and 1 (action/command ID), adding
optional key 2 (numeric field ID → argument value map). Declarative action
responses contain key 0 (field ID → decoded integer map), key 1 (actual RX byte
strings) and key 2 (capture truncated). Legacy drivers retain the empty response.
Capture is bounded to eight reads of up to 32 bytes each.

The `device-action` rule invokes an action on matching records. Configuration:
1 source module key; 2 optional source action ID (0 = any); 3 target module key;
4 target action ID; 5 optional source field; 6 optional argument ID;
7 optional unsigned constant; 8 trigger (0 every record, 1 rising, 2 falling, 3 latch only, 4 latch and execute).
Source field values preserve their type when forwarded; a constant takes
precedence. Returned action records enter the runtime queue and can feed further
rules. Command chains are bounded to eight hops, including derived records.
The module-manager busy guard serializes access to each device context.

Run Deploy now generates and installs wire-v2 profiles before validating and
applying configuration. Canvas activation and parameter wires become
`device-action` rules. Source keys may identify derived processing records as
well as physical modules; target module keys retain strict module references.

Parameter updates are retained in the device context. Latch-only updates never
access the bus. Missing required parameters defer explicit activation; the
pending bit is cleared after successful execution. Repeated pending activation
coalesces into one execution. Implicit data-driven execution waits for all
required values without reporting an action failure. Parameters and published
result fields are released when the device is deinitialized.

Opcode 28 LOAD_VALUE has the same operands as LOAD_ARGUMENT and reads a previously
published field from the device’s variable memory, falling back to its configured
default. Opcode 27 SCALE_PACK uses
`[27, dst, src, flags, width, divisor, multiplier_i32, offset_i32]`.
Flags: bit 0 input big-endian, bit 1 input signed, bit 2 output big-endian.
Arithmetic is checked signed 64-bit `(input * multiplier) / divisor + offset`,
with division truncating towards zero. Output width is 1–8 bytes; range errors
fail rather than wrap. COPY_BYTES imm1 supplies a checked source byte offset.
The opcode version is 4; older profiles remain supported.

The ESP32-S3 configuration owns byte buffers of 32 bytes. LOAD_CONST still loads
at most eight bytes; CONCAT assembles larger messages before one I²C transfer.
Reads generated by the editor remain bounded to eight bytes. Numeric schemas
remain INT64/UINT64; floating point is not introduced.

Installed profile CBOR is stored in the Zephyr Settings/NVS namespace
`device_profiles/<slot>` and loaded before startup configuration validation. Removal
deletes the stored slot after checking live references. A missing profile in a
stored configuration leaves the Core reachable for repair instead of aborting boot.
Read records and result-schema descriptors use bounded temporary heap allocations
to avoid overflowing the small runtime worker stack.

Validation: signed ESP32-S3 build and native tests covering communication,
module manager, profiles, typed argument validation, pending activation with
separate inputs, shared result memory, a 28-byte OLED transaction, decoder byte
offsets, checked signed scaling, and runtime filtering/forwarding.

Hardware verification: OLED at 0x3C, SDA GPIO38 and SCL GPIO37. A production-generated
profile sent the complete 28-byte initialization message with two canvas input
parameters. Configuration validation and readback passed; after a physical reboot
the driver and its runtime configuration remained installed, parameter rules
repopulated input memory, and the action succeeded without explicit arguments.
The original configuration was restored and test profiles removed. Write-only
actions correctly return an empty RX array.
